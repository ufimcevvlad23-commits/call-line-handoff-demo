# Скорозвон → Битрикс24 Call Bridge

Предпусковой контур для передачи квалифицированного звонка актуализатора менеджеру с сохранением фактического Caller ID. Система уже умеет собирать звонки Скорозвона, принимать CRM-форму, создавать лид, сопоставлять имитированный или реальный CDR и готовить звонок менеджера через Asterisk. Реальные вызовы включаются отдельным флагом только после подключения SIP-транка.

## Текущий безопасный режим

- `INGESTION_ENABLED=true`: защищённая CRM-форма может создавать лиды.
- `SKOROZVON_POLL_ENABLED=true`: фоновый сбор сохраняет подключённые разговоры, но сам не создаёт лиды.
- `PBX_CDR_ENABLED=true`: CDR можно принимать и сопоставлять.
- `CALLING_ENABLED=false`: ни один запрос менеджера не может запустить реальный звонок.
- Если Caller ID отсутствует, лид создаётся со статусом `Ожидает определения исходящего номера`.
- Номер считается готовым только при одновременном наличии в `ALLOWED_CALLER_IDS` и `LINE_MAP_JSON`.
- Секреты находятся только в закрытом серверном `.env.production` и не попадают в репозиторий или браузерный код.

## Поток данных

1. Фоновый worker читает последние успешные исходящие разговоры Скорозвона и сохраняет `call_id`, `session_id`, `external_access_id`, телефон, актуализатора и время.
2. CRM-форма Скорозвона вызывает `POST /api/skorozvon-event`. Если форма не передала `call_id`, система ищет разговор по Session ID, External access ID, затем по телефону и времени; при необходимости сразу обновляет последние звонки через API Скорозвона. Повтор обновляет существующую запись и не создаёт дубль.
3. Лид создаётся на первой стадии, назначается указанному менеджеру и получает технические поля и подписанную ссылку менеджера.
4. `POST /api/pbx-cdr` сопоставляет фактический Caller ID по `call_id`, затем `session_id`, затем по телефону и окну ±20 минут.
5. Если Caller ID разрешён и привязан к SIP endpoint, лид получает состояние `Готово к звонку менеджера`.
6. Подписанная кнопка менеджера через AMI сначала звонит менеджеру, после ответа — клиенту с сохранённым Caller ID.

## Хранилище и надёжность

SQLite хранит звонки, CDR, CRM-состояния, аудит и состояние интеграций. Для Битрикс24 действует очередь повторов с экспоненциальной задержкой. Worker запускается внутри сервиса каждые 30 секунд. Отдельные systemd timers выполняют проверку здоровья раз в две минуты и ежедневный SQLite backup с 14-дневным хранением.

Состояния вызова:

- `observed` — успешный разговор найден в Скорозвоне, CRM-форма ещё не передана;
- `waiting_caller_id` — лид создан, АТС ещё не определила фактический исходящий номер;
- `caller_unverified` — номер получен, но отсутствует в белом списке или карте SIP-линий;
- `ready` — номер и линия подтверждены;
- `call_requested` — менеджер запустил вызов;
- `call_failed` — Asterisk не принял запрос.

## API

### `POST /api/skorozvon-event`

Bearer: `SKOROZVON_WEBHOOK_SECRET`.

```json
{
  "call_id": "call-1042",
  "session_id": "session-777",
  "external_access_id": "external-9",
  "client_phone": "+79991234567",
  "entity_type": "lead",
  "result": "qualified",
  "actualizer": "Имя актуализатора"
}
```

`successful_caller_id` можно передать сразу, но до появления собственной АТС источником истины для него остаётся CDR.

### `POST /api/pbx-cdr`

Bearer: `PBX_CDR_SECRET`. В production Nginx должен принимать этот маршрут только с localhost.

```json
{
  "event_id": "cdr-9001",
  "call_id": "call-1042",
  "session_id": "session-777",
  "client_phone": "+79991234567",
  "caller_id": "+79031112233",
  "disposition": "ANSWERED",
  "occurred_at": "2026-09-10T15:30:00Z"
}
```

### `POST /api/call`

Принимает только подписанный запрос со страницы менеджера или отдельный Bearer. Всегда проверяет номер по серверному белому списку. При `CALLING_ENABLED=false` возвращает `503` до обращения к Asterisk.

### `GET /api/admin/summary`

Bearer: `DASHBOARD_ACCESS_TOKEN`. Возвращает агрегаты, последние 50 записей с маскированными телефонами и безопасный аудит. Панель доступна на корневом URL и хранит код только в `sessionStorage` текущей вкладки.

## Переменные окружения

Полный шаблон находится в `.env.example`. Обязательные группы:

- Битрикс24: webhook, ID менеджера, первая стадия лида и имена пользовательских полей;
- Скорозвон: логин API, API-ключ, ID/секрет приложения, секрет CRM-формы;
- хранилище: `DATABASE_PATH`;
- CDR и панель: отдельные длинные секреты;
- телефония: `ALLOWED_CALLER_IDS`, `LINE_MAP_JSON`, AMI и канал менеджера;
- предохранитель: `CALLING_ENABLED=false` до приёмочных SIP-тестов.

## Битрикс24

`scripts/configure-bitrix.mjs` идемпотентно создаёт поля:

- телефон клиента;
- успешный Caller ID;
- SIP endpoint;
- Call ID, Session ID и External access ID Скорозвона;
- актуализатор;
- статус передачи;
- последняя ошибка;
- подписанная ссылка менеджера.

Новые лиды создаются со `STATUS_ID=NEW` и `ASSIGNED_BY_ID`, указанным в серверной конфигурации.

## Asterisk: подготовлено, но не активировано

`deploy/prepare-asterisk.sh` сначала маскирует сервис, затем устанавливает пакет и помещает шаблоны в `/etc/asterisk/callbridge-staged`. Asterisk остаётся остановленным и замаскированным, поэтому не открывает SIP-порт.

Подготовлены:

- два шаблона IP-транка Билайна;
- endpoint Скорозвона и закрытый входящий контекст;
- dialplan «сначала менеджер, затем клиент»;
- AMI только на `127.0.0.1` с ограниченными правами;
- AstDB-белый список `callbridge-caller-route/<номер>`;
- `scripts/sync-asterisk-allowlist.mjs`: без `--apply` выполняет только проверку, с `--apply` синхронизирует номера.

## Проверка без реальных звонков

```text
npm test
```

Тесты покрывают нормализацию номеров, форму без Caller ID, идемпотентность, сопоставление CDR по сессии и по времени, белый список, очередь повторов, подписанные ссылки и AMI Originate через локальный имитатор. Ни один тест не подключается к SIP-транку и не звонит на телефон.

## Развёртывание

- приложение: `/opt/skorozvon-bitrix-call-bridge`;
- SQLite и backups: `/var/lib/skorozvon-call-bridge`;
- systemd: `skorozvon-call-bridge.service`;
- локальный HTTP: `127.0.0.1:8790`;
- публичный HTTPS: Nginx → локальный HTTP.

После загрузки файлов и обновления закрытого env:

```text
sh deploy/install-or-upgrade.sh
```

Скрипт не меняет `CALLING_ENABLED`. Включение телефонии выполняется только отдельным финальным действием после того, как Билайн разрешил IP сервера, предоставлен полный список номеров и выполнен контролируемый тест на согласованный номер.

## Что останется после выдачи SIP-доступа

1. Подставить подтверждённые адреса/порты и IP-идентификацию в staged-конфиги.
2. Получить полный список номеров и соответствие номер → транк.
3. Запустить dry-run белого списка, затем применить его к AstDB.
4. Снять маску Asterisk, проверить регистрацию/OPTIONS и CDR без исходящего INVITE.
5. Провести один согласованный тест актуализатора и один тест менеджера.
6. Только после успешного Caller ID и аудита установить `CALLING_ENABLED=true`.
